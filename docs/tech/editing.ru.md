# Правка текста: решения

Почему некоторые команды правки устроены так, как устроены. Код — `EditorView*.cs`; документация для пользователя —
README и F1.

## Где код (`src/BlueEdit`)

Редактор начинался как операторы верхнего уровня в одном `Program.cs` с локальными функциями, делившими его
переменные; на 2 333 строках в нём трудно было что-то найти. В октябре 2026 он стал частичным классом `App`: те
переменные — его поля (с типами, какие у них были у компилятора), настройка — его конструктор в том же порядке,
локальные функции — методы, по темам в `App.Menus.cs`, `App.Documents.cs`, `App.Search.cs`, `App.Settings.cs`,
`App.Status.cs`, `App.Proofing.cs`, `App.ProofingSetup.cs` и `App.Code.cs` (100–530 строк каждый). Сделано
программой по синтаксическому дереву (Roslyn), а не руками, так что переехал только текст; в `Program.cs` осталась
командная строка (`--help`, `--install-proofing`...). Исходники переехали из корня в `src/BlueEdit` рядом с
`src/Tui`; `BlueEdit.csproj` остался в корне, где его читают скрипты и откуда берётся версия.

## Команда — `be`

Программа называется BlueEdit, а файл и команда — `be` (`be.exe`), с 20 октября 2026. Консольный редактор набирают по
многу раз в день, и такие команды короткие: `vi`, `nano`, `mc` для Midnight Commander. Раньше файл был `blueedit.exe`,
а рядом лежал незаметный `be.cmd`. Старое имя не сохраняется (ни ссылки `blueedit`, ни переходника): редактор ещё не
был публичным, и единственную настройку под него (ассоциацию в Far, `EDITOR`/`VISUAL`, PATH) перевели вручную. Другой
команды `be` на проверенных системах (Windows и две Linux-машины) не нашлось. Папки сохранили имена
(`%APPDATA%\blueedit`, `%LOCALAPPDATA%\BlueEdit`): в них настройки и проверяльщики, а не команда.

## Интерфейс на других языках (`Ui.cs`, `lang/*.json`)

- **Таблица на язык, ключ — английская строка.** `lang/ru.json` сопоставляет `"_File"` и `"_Файл"`; код пишет
  по-английски и пропускает строку через `T()`. Номеров и имён ключей нет: английский текст в коде остаётся читаемым
  источником, а строка, которой нет в таблице, показывается как написана. Это и есть запасной вариант, поэтому
  пропуск или старая таблица интерфейс не ломают. Таблица — JSON с комментариями, встроена в редактор; файл с тем же
  именем в папке настроек `lang/` добавляет язык или меняет строки без сборки.
- **`uiLanguage`**: `auto` (язык интерфейса системы; на Linux .NET берёт его из `LANG`), `en` или код; `ru-RU`
  сводится к `ru`. `BLUEEDIT_UI_LANGUAGE` важнее настройки; UI-тесты ставят `en`, чтобы их проверки английского текста
  работали на любой системе.
- **Буква меню — это клавиша, а не символ.** Меню получает Alt раньше редактора (`TuiApp`), поэтому буква русского
  меню не должна быть одной из Alt-клавиш редактора (C D G H I L M N Q R X Z). Каждая буква сводится к своей клавише
  QWERTY (`KeyboardLayout.Latin`, теперь и Х Ъ Ж Э Б Ю Ё), так что Alt+Ф и Alt+A открывают одно меню в любой
  раскладке. Строка меню: `_Файл Пр_авка П_оиск В_ид Фор_мат Инстр_ументы Б_лок Ок_но Помо_щь`. «Справка» не
  получилась: её единственная свободная буква, А, занята Правкой. `UiTests` проверяет каждую таблицу: каждый ключ ещё
  есть в коде строкой; каждая подпись меню переведена и отмечает одну букву; два меню или два пункта одного меню не
  сидят на одной клавише (`MenuBar` их не примет); ни одно меню не занимает Alt-клавишу редактора.
- **Значения вставляются по номеру.** `T("Save changes to {0}?", name)` (`Tf` в `App.cs`): в ключе остаются `{0}`,
  `{1}`, и перевод ставит их в своём порядке («Символов, которых нет в {1}: {0}»). Склейка английских кусков закрепила
  бы английский порядок слов. Таблица пользователя с неверными местами даёт английский текст, а не исключение;
  `UiTests` проверяет, что во встроенных таблицах места те же, что в ключах.
- **Одно английское слово в двух местах** может требовать двух слов: «Save» под F2 — «Сохр» (подсказки короткие), на
  кнопке — «Сохранить». `Ui.Tc("hint", "Save")` ищет сначала `"hint|Save"`, потом `"Save"`. Так же сделаны кнопки
  вопроса о восстановлении (`recover|Discard` — «Удалить копии», а «Discard» несохранённого файла — «Не сохранять»).
  Только там, где это нужно таблице: правило — один ключ на английскую строку.
- **Слова самого терминального слоя** (подсказки вроде «Enter = OK   Esc = Cancel», «File name: », «Drives») идут
  через `Tui.Strings.T`, которую редактор направляет в свои таблицы. `src/Tui` об `Ui.cs` ничего не знает.
- **Буквы в окнах — тоже клавиши.** Кнопка нажимается первой буквой, теперь она сравнивается как клавиша
  (`KeyboardLayout.Latin`), так что «Сохранить» — клавиша С в любой раскладке; кнопки одного вопроса в каждой таблице
  начинаются с разных букв («Восстановить, Удалить копии, Позже»). Флажок поиска отмечает свою букву подчёркиванием,
  как пункт меню (`FormToggle("Match _case")`; «_Учитывать регистр» — Alt+У, клавиша E). Раньше буква была отдельным
  символом и искалась в подписи, а в переводе её нет.
- **Числа берут формы языка.** `Ui.N(n, "Saved {0} file", "Saved {0} files")` (`Tn` в `App.cs`): ключ — второй
  аргумент; таблица даёт формы через `|` — две, как в английском, или три для русского («Сохранён {0} файл|Сохранено
  {0} файла|Сохранено {0} файлов»): первая для 1, 21, 101; вторая для 2–4, 22–24, но не 12–14; третья для остальных.
  Правило выбирается по числу форм, поэтому таблице не нужен код; это правило русского (а также украинского и
  белорусского), но не польского, где первая форма только для 1.
- **Короткие слова строки состояния** («Ln», «Col», «STREAM», «SPELL», «2E 1W») — ключи `status|…`: «Стр», «Кол»,
  «ПОТОК», «ОРФО», «2о 1п». UI-тесты ждут «Ln », чтобы понять, что редактор запустился; русские ждут «Стр ».
- **Тесты, переключающие язык, идут отдельно** (коллекция xUnit без параллельного запуска): язык общий для всего
  процесса, а другие тесты читают английские сообщения.
- **Встроенная таблица полная.** `UiTests` собирает все строки, которые код передаёт в `T()`/`Tf()`/`Strings.T()`, и
  падает, если во встроенной таблице какой-то нет: новая строка окна не уйдёт непереведённой случайно. Таблицы в
  папке настроек могут быть неполными.
- **Сделано пока:** меню, подсказки клавиш, повседневные окна (несохранённые изменения, сохранить как, открыть, файл
  изменён на диске, восстановление, поиск, замена, поиск в папке, переход к строке, переименование, кодировки) и
  Инструменты > Настройки с пояснениями; строка состояния и её сообщения; окна настройки (проверка грамматики и её
  модели, языки, источник и словари орфографии, инструменты для кода, шрифт терминала, пропускаемые правила, стиль),
  Файл > Сведения и ошибки в формулах. И справка F1. Ещё по-английски только то, что говорят другие программы
  (сообщения языкового сервера, текст исключений; пояснения модели и так идут на языке абзаца).
- **Справка F1 — текст на каждый язык, разделами** (`lang/help.<код>.md`, встроенный; файл в папке `lang/`
  настроек важнее), а не таблица её строк: перевод пишет свои слова, в своём порядке и своей длины. `HelpTextTests`
  следит за соответствием: разделы английской справки в том же порядке (F1 открывает раздел по его месту), и названы
  все F-клавиши и сочетания с Ctrl английской справки, в том же разделе (Alt+буква не проверяется: буквы меню в
  языках разные). Файл встраивается с `WithCulture="false"`: MSBuild читает `.ru.` в `help.ru.md` как культуру и унёс
  бы его в сателлитную сборку (`ru\be.resources.dll`), которую однофайловый `be.exe` не загружает. Новый язык
  начинается с `lang/template/strings.json` (все строки интерфейса, пустые) и `lang/help.en.md`
  (`lang/template/README.md`).

## Справка F1: разделы, раскладывает редактор (`HelpText.cs`, `HelpDialog`)

До октября 2026 справка была одним текстом, выровненным вручную, `lang/help.en.txt`: две колонки «клавиша —
действие», 155 строк одним свитком, всё одним цветом, в 86 колонок. Пользователю она читалась тяжело («буквы
сливаются, всё слишком просто расположено»: заголовки не выделяются, клавиши не отделены, частям тесно) и плохо
переводилась: переводчику приходилось считать пробелы, чтобы держать колонки, и переносить строки вручную.

Теперь исходник говорит, что такое каждая строка, а раскладывает редактор:

```
# Файлы

F2, Ctrl+S         | Сохранить
Shift+F2           | Сохранить как...

В «Открыть» и «Сохранить как»: F7 — новая папка, ...
```

`# Заголовок` начинает раздел; `клавиши | что делают` — строка клавиши (пробелы перед `|` только для глаза); любая
другая строка — абзац, идущие подряд строки склеиваются. `HelpDialog` показывает заголовки разделов слева и выбранный
справа: заголовок белым, клавиши — своей колонкой, цветом букв меню (слишком длинная для колонки, больше 26, — на
своей строке, текст под ней), текст переносится рядом с ними, абзацы — по ширине, между частями пустая строка. Вверх
и вниз выбирают раздел, PgUp/PgDn, Пробел, Home/End и колесо листают его (▼ ▲ в строке клавиш — что есть ещё), Esc,
Enter или F1 закрывают.

F1 открывается на разделе под вид файла: Markdown в Markdown-файле, Code в языке с языковым сервером, иначе
«Основное». В переводе раздел находится по месту английского заголовка, поэтому перевод держит разделы в том же
порядке (это проверяет тест).

Содержание — всё из старой справки, в 14 разделах; по строке на клавишу там,
где старая ставила две клавиши в одну строку.

## `be` в любой консоли (`UserPath.cs`)

Релиз — это zip: распакованный в «Загрузки», `be.exe` запускается только из своей папки. **Инструменты > Команда be
в любой консоли** добавляет эту папку в пользовательский PATH или убирает её, если она там есть; только для Windows
(в Linux и macOS показывается `ln -s` в `~/.local/bin`).

- **PATH пользователя, а не системы**: `HKCU\Environment\Path` принадлежит самому пользователю, поэтому не нужны ни
  права администратора, ни вопрос UAC; Windows добавляет его после системного PATH в каждом новом процессе.
- **Пишется как хранится**: читается с `DoNotExpandEnvironmentNames` и записывается обратно с тем же типом
  (`REG_EXPAND_SZ`). `Environment.SetEnvironmentVariable(…, User)` не подошёл: он пишет обычный текст, и записи вроде
  `%USERPROFILE%\bin` сохранились бы раскрытыми, так что последующая смена переменной до них бы уже не доходила.
- **Одна запись**: папка сравнивается с каждой записью в раскрытом виде, без обратной косой черты в конце и без учёта
  регистра; при удалении убираются все её копии.
- **Только новые консоли**: после записи всем окнам рассылается `WM_SETTINGCHANGE "Environment"`, и Проводник и
  запущенный после этого Windows Terminal читают новый PATH; уже открытые консоли сохраняют свой (строка состояния
  об этом говорит). В приветствии не предлагается: это изменение системы для всех программ, поэтому оно остаётся
  выбором в меню.

## Первый запуск (`Welcome` в `App.Settings.cs`)

Новый пользователь открывает консольный редактор и видит пустую страницу: на нижней строке есть F1 и F9, но ничто не
говорит, что орфография уже работает и что проверку грамматики можно настроить. Поэтому при первом запуске
показывается одно окно: клавиши для начала (меню, справка, сохранить, открыть, выйти), языки орфографии, которые уже
работают (или где взять словари, на Linux), строка о проверке грамматики и её вариантах и три кнопки: «Начать» (и Esc,
и Enter), «Грамматика...» (открывает Инструменты > Настроить проверку грамматики) и «Язык...» (языки интерфейса, каждый
назван своими словами, ведь пользователь может не читать язык экрана; английский, пока не выбран другой). Кнопка не
«Русский»: редактор для всех, а новые таблицы (`lang/*.json`) сами появляются в списке.

- **Одно окно, не мастер.** Мастер из нескольких страниц подходит установщику; здесь редактор уже запущен, и каждый
  его шаг — пункт меню. Окно только показывает на них; ничего не ставится и не меняется, пока не выбрано. Консольный
  мастер ещё и отличался бы от остальных окон редактора без пользы.
- **«Первый запуск» — это «нет settings.json».** Любой выбор (и Esc) записывает settings.json из шаблона, поэтому окно
  показывается один раз без отдельного флажка. У существующего пользователя файл есть, и он окна не увидит; кто удалит
  файл, увидит снова — это и есть начало с чистого листа.
- **Запуск из git или другой программы** (EDITOR) при самом первом запуске тоже покажет окно: Esc — и дальше к файлу.
  Проверять, кем запущен редактор, ради этого не стоит.
- UI-тесты ставят `BLUEEDIT_WELCOME=0` (у каждого теста пустая папка настроек); показывает окно `test_settings.py`.
- Проход в Sandbox (`tasks newcomer`) снимает его перед Esc.

## Сохранение (`SafeFile.cs`, `Write` в `App.Documents.cs`)

- **Через временный файл.** Текст пишется в `.<имя>.<случайное>.tmp` рядом с файлом, сбрасывается на диск и потом
  одним шагом встаёт на место старого файла (`File.Replace`, в Windows это `ReplaceFile`; в Linux — переименование).
  Раньше файл писался поверх (`File.WriteAllBytes`): если посреди записи пропадало питание, кончалось место или
  процесс убивали, оставался обрезанный файл, а старого текста уже не было.
- **Свойства старого файла сохраняются.** В Windows `ReplaceFile` сохраняет его атрибуты, права и время создания;
  в Linux права (биты rwx) копируются, потому что переименование их не сохранило бы. Символическая ссылка остаётся
  ссылкой: заменяется файл, на который она указывает. Не сохраняются жёсткие ссылки (под другими именами остаётся
  старый текст) и в Linux владелец, если редактор запущен от другого пользователя, которому можно писать в папку. Ни
  того, ни другого к моменту написания не встречалось.
- **Файл «только для чтения» таким и остаётся.** Для переименования нужна только запись в папку, так что в Linux оно
  заменило бы файл только для чтения. Поэтому старый файл сначала открывается на запись (и закрывается, не
  меняясь); это не удаётся там же, где не удавалась запись поверх: нет прав, файл только для чтения или его держит
  программа, которая ни с кем его не делит (так Word держит открытые документы).
- **Папка, в которой нельзя создавать файлы** (можно писать только в сам файл): запись поверх, как раньше.
- **Если сохранить не удалось, об этом говорит окно** «Not saved» с причиной от системы; документ остаётся
  несохранённым, и при закрытии редактор по-прежнему спрашивает. Раньше исключение никто не ловил: редактор
  закрывался вместе со всеми несохранёнными документами. «Сохранить как» с ошибкой оставляет документу прежнее
  имя. Тесты: `EditorTests` (не остаётся временного файла, заблокированный файл, ссылка, права в Linux) и UI-тест
  `test_a_file_that_cannot_be_written_says_so_and_the_editor_stays`, который падал на коде до этого изменения.

## Восстановление (`Recovery.cs`, `StoreRecovery` в `App.Documents.cs`)

Автовосстановление, как в Word: то, что набрано после последнего сохранения, переживает убитый процесс, ошибку или
пропадание питания — кроме последних нескольких секунд.

- **Копии, а не сами файлы.** Каждые `autoRecoverSeconds` секунд (по умолчанию 10, 0 — без копий) документы с
  несохранёнными правками пишутся в `session-<id процесса>-<случайное>.json` (свой файл на каждый запуск) в `%LOCALAPPDATA%\BlueEdit\recovery`
  (`~/.local/share/...` в Linux): путь, текст, кодировка, концы строк. Сохранять в сам файл пользователя отвергнуто:
  недописанная правка попала бы в файл, за которым следят git, сборка или Obsidian.
- **Набор не ждёт.** В потоке редактора текст только склеивается в строку (копия строк, которые он меняет); JSON и
  запись идут в фоне, пока идёт одна запись, следующая пропускается (догонит более поздняя), а тот же текст второй раз не пишется. Неудачная
  запись молча пропускается: следующая попробует снова.
- **Ошибка, которая закрывает редактор** (никем не пойманная, вокруг `app.Run`), сразу пишет копии, возвращает
  терминал, говорит, где лежит текст, и даёт ошибке завершить процесс, как раньше. Не покрыто: ошибки в других
  потоках, а также убитый процесс и пропавшее питание — тогда остаётся последняя копия по таймеру.
- **Обычный выход удаляет копию**; после каждого сохранения она переписывается без сохранённого документа.
- **Следующий запуск** ищет копии, чей редактор не работает: копия называет свой процесс номером *и* временем
  запуска, и процесс должен быть BlueEdit. Номера процессов используются повторно: в UI-тестах, идущих параллельно,
  номер убитого редактора за секунды доставался другому BlueEdit, и по одному номеру его копия пропускалась как копия
  работающего (так упал CI). Свой файл на каждый запуск к тому же не даёт редактору со старым номером
  перезаписать, а потом удалить копию прежнего владельца номера. `HasExited` не спрашивается: процесс другого
  пользователя отвечает на это «Access is denied» (в тестах с номером 0); время запуска, которое не прочесть,
  считается совпавшим. Копия старше своего файла (файл сохранили после неё) или
  совпадающая с ним пропускается. Остальные предлагаются в одном окне: *Recover* открывает их как несохранённые
  документы (для файла считается, что открыт он такой, какой на диске сейчас), *Discard* удаляет копии, *Later*
  оставляет их до следующего запуска.
- Несколько одновременно запущенных редакторов держат каждый свою копию и чужие не предлагают.
- Тесты: `RecoveryTests` и UI-тест `test_unsaved_text_of_a_killed_editor_is_offered_at_the_next_start` (редактор
  убивают после копии, следующий запуск восстанавливает текст, сам файл не тронут). У пути ошибки вокруг `app.Run`
  теста нет: в редакторе нечем намеренно вызвать там исключение.

## Форматирование абзацев (`EditorView.Paragraph.cs`)

DOS-редакторы умели переразбивать абзац под поле и выравнивать его; в BlueEdit был только мягкий перенос.

- **Что такое абзац.** Соседние непустые строки. В Markdown заголовок или пункт списка начинает свой абзац, а строки,
  которые не текст (блоки кода, таблицы, формулы на отдельных строках, заголовки), не трогаются — та же проверка
  `ProseLine`, что и у грамматики. Абзац проверки грамматики (`ParagraphAt`) не используется: он склеивает абзацы
  через пустую строку вокруг формулы — это верно для предложения, которое продолжается после формулы, и неверно
  для переразбивки.
- **Выделение** переразбивает каждый абзац внутри него отдельно (склеить все в один — испортить текст), начиная с
  последнего, чтобы номера строк выше не сдвигались; всё вместе — один шаг отмены.
- **Слова.** Куски между пробелами, но формула в строке (`$…$`) или код (`` `…` ``) — одно слово вместе с пробелами:
  перенос строки внутри сломал бы формулу. Слова не переносятся по слогам и не режутся; слово длиннее поля получает
  отдельную строку.
- **Префиксы.** Первая строка сохраняет отступ, знаки цитаты (`> `) и маркер списка (`- `, `1. `); следующие строки
  получают знаки цитаты и пробелы шириной маркера, так что текст пункта висит под собой — так Markdown понимает, что
  строки остались в пункте.
- **По правому краю, по центру и по ширине — только в обычном тексте.** Они работают добавлением пробелов; Markdown при
  показе схлопывает пробелы, так что там они ничего видимого не изменили бы и оставили мусор в исходнике.
  Переразбивка и выравнивание влево там уместны. В коде ничего этого нет: перенос строки или пробелы меняют смысл кода.
- **По ширине** = переразбивка, затем растягивание всех строк, кроме последней: лишние пробелы отдаются промежуткам
  слева. Влево, вправо и по центру — переносы строк остаются, как были.
- **Автоперенос** (`autoWrap`, по умолчанию выключен) срабатывает после каждого набранного символа, кроме пробела: если
  курсор зашёл за поле, строка режется по последнему пробелу не дальше поля, остаток уходит на новую строку с
  префиксом продолжения. Это тот же шаг отмены, что и набор. Пробел за полем ждёт следующего слова. Одно слово длиннее
  поля не режется.
- Поле — настройка (`rightMargin`, 78 — классическая ширина, оставляющая место для знака цитаты в ответах), а не
  ширина окна: файл не должен зависеть от того, какой ширины оказался терминал.

## Выносные формулы в несколько строк (`LatexLayout.cs`)

Режим чтения показывал выносную формулу одной строкой Unicode (`Latex.ToUnicode`): `\frac{x^2+1}{2x-3}` становилось
`(x²+1)/(2x-3)`. В заметках, для которых он нужен (хранилище учебных заметок по математике, замер 6 октября 2026:
614 заметок, 99 478 формул в строке и 16 205 выносных), в 40 % выносных формул есть `\frac`, в 2570 — строки (`aligned`, `gathered`,
`array`), а `\left…\right` встречается 7348 раз. Хуже всего читается дробь через косую черту.

- **Как**: небольшая раскладка блоков, как у pretty printer в sympy. Каждый кусок — строки текста с базовой строкой;
  куски стоят рядом по базовой линии, дробь — числитель / черта `─` / знаменатель, корень — черта над подкоренным
  выражением, у `∑` и `lim` пределы сверху и снизу, `\left(…\right)` растёт `⎛⎜⎝`, `aligned` / `cases` / `array` /
  матрицы — сетки (пары выравнивания вправо, затем влево, `cases` со скобкой `⎧⎨⎩`, у массива его `l c r`, `\hline` —
  линия), `\vec` и `\overline` — знак сверху, `\underbrace` — `╰─┬─╯` с подписью, `\boxed` — рамка, `\tag` справа.
  Каждый символ — одна колонка.
- **Между дробью и множителем рядом с ней** ставится пробел (`6/7 x`, а не `─x`), а в однострочном виде дробь перед
  множителем берётся в скобки: `(6/7)x^(7/2)`, а не `6/7x^(7/2)`, что читалось как 6/(7x); `x³/3`, а не `(x³)/3`
  (10 октября 2026, на разобранном в заметках интеграле).
- **Корень в один ряд** пишется в один ряд, `√3` или `√(b² - 4ac)`: черта отдельным рядом висела над знаком, глиф
  которого не доходит до верха ячейки (замечено в работе, 10 октября 2026). Над более высоким черта остаётся.
- **Интегралы** — `⌠⎮⌡` высотой с подынтегральное выражение и не ниже трёх строк, пределы справа сверху и снизу
  (10 октября 2026; раньше `∫` в одну строку рядом с трёхэтажной дробью выглядел маленьким).
  Подынтегральное выражение идёт до ближайшего отношения (`dx = …`) или следующего интеграла, так что дробь после `=`
  знак не растягивает. У `∮` в Unicode нет высокой формы, он остаётся в одну строку.
- **Индексы и степени остаются одной строкой**: надстрочными символами, если в Unicode есть все (`x²`, `aᵢⱼ`), иначе
  выписанными строкой выше или ниже (`e` с `-x²/2` над ним). Поднимать целые блоки для каждой степени — формулы
  становятся вдвое выше, а читать легче не становится.
- **Пробелы как в печати** (`Latex.SpacedChar`, `KeepSpace`; 11 октября 2026), в однострочной форме и в многострочной:
  показываются не пробелы исходника, как и в TeX. Отношение (`=`, `<`, `>`, а также `≤`, `≠`, `∈` … из команд) получает
  пробел с обеих сторон, `+` и `-` тоже, если они не знак числа (в начале, после операции или открывающей скобки: `-b`,
  `(-1)`); степени, индексы и однострочные дроби — слитно (`e⁻ˣ⁺¹`, `i=1` под `∑`), как TeX набирает индексы; пробел
  между числом и буквой убирается (`2 a` — это `2a`); `\text{…}` остаётся как написан. Знак перед многоэтажной дробью
  отделён от её черты («- ─», а не «-─», что читается как одна длинная черта). Зачем: книга в хранилище, переведённая из
  PDF, пишет `a^{2}+\frac{2 a}{n}<2`, и её формулы выходили как `a²+─<2` и `2 a` — читать трудно, а записи, набранные
  вручную с пробелами, выглядели нормально (замечено в работе, 11 октября 2026). Кернинга в моноширинном терминале нет:
  настраивать можно только эти пробелы.
- **Куда идут строки**: редактор и так раскладывает строки файла по экранным строкам (мягкий перенос), поэтому картинка
  формулы отдаётся строкам её блока `$$` или `\[ … \]` по очереди, а последняя строка блока берёт оставшиеся
  (`Disp.RowWidth`: «строка», у которой сегменты переноса — строки картинки). Курсор, прокрутка и таблица строк
  работают без изменений. Строки `$$`, `\[` и `\]` остаются пустыми вокруг.
- **Live-просмотр** тоже рисует картинки (10 октября 2026), кроме формулы, в которой стоит курсор: все её строки
  вместе с разделителями показываются как написаны, пока курсор на любой из них, как в Obsidian. Пока курсор ходит
  внутри формулы, высота под ним не меняется, а вход в неё и выход заново раскладывают только строки этого блока
  (`FormulaLines`, `LiveRowChanged`). Раньше Live картинок не рисовал совсем: как написана показывалась только строка
  с курсором, и картинка меняла бы высоту под ним.
- **Строка текста с высокой строчной формулой** (`$…$` с дробью, высоким интегралом, степенью без надстрочных символов
  в Unicode, как `x^{5/2}`) тоже раскладывается в несколько рядов, слова стоят на базовой линии формул
  (`Conceal.InlinePicture`, 10 октября 2026): «Интеграл: ∫₁³ (3x^(5/2) + x²)dx» в одну строку читался
  плохо. Строка, где все формулы помещаются в один ряд (`x²`, `α ≤ β`), остаётся одной строкой и переносится, как
  раньше. В Live строка с курсором показывается как написана, поэтому при входе курсора она становится однорядной.
- **Когда не используется** — тогда однострочный вид: перенос выключен (тогда одна строка — один экранный ряд); картинка
  шире окна (длинная строка с высокой строчной формулой тогда переносится в однорядном виде).
- **Замер**: все 15 859 выносных формул хранилища разложены без единого исключения, 10 489 из них — больше чем в одну
  строку; ширина в медиане 23 колонки, у 90 % не больше 46, самая широкая — 213; высота в медиане 3 строки, у 90 % не
  больше 6. Команды, оставшиеся как написаны: `\not` 14 раз, `\substack` вне пределов 11, несколько более редких.
  Заметка в 7525 строк с 815 выносными формулами рисуется в режиме чтения за 5 мс вместе с раскладкой всех строк;
  картинки кэшируются по тексту формулы.

## Картинки формул (Sixel)

Второй шаг после раскладки текстом выше: выносные формулы набираются и показываются картинками там, где терминал
умеет их показывать (документация для пользователя: [formula-pictures.ru.md](../formula-pictures.ru.md)). Просили
сделать это частью, которую включают, а не для всех (10 октября 2026).

- **Дополнительный модуль, загружаемый из папки** (`src/MathImages`, `FormulaImages.cs`). CSharpMath (движок
  раскладки TeX для .NET, MIT) рисует через SkiaSharp (MIT), у которого одна нативная библиотека — 11,6 МБ, а весь
  модуль — 14 МБ: больше, чем нужно остальному редактору, ради возможности, которой пользуются немногие. Поэтому он —
  отдельный файл релиза (`blueedit-mathimages-<версия>-win-x64.zip`, `…-linux-x64.tar.gz`) и загружается, если найден,
  в собственный `AssemblyLoadContext`; редактор на него не ссылается и находит `Renderer.Render` по имени, проверяя
  `Renderer.Api`. В процессе редактора, а не во вспомогательном процессе: тому понадобилась бы своя среда .NET
  (редактор — один самодостаточный файл). Формула, которую модуль не может прочитать, возвращается с сообщением
  CSharpMath, а исключение из модуля оставляет эту формулу текстом; падение внутри нативного кода Skia уронило бы
  редактор — на 17 222 формулах ниже такого не было.
- **Почему CSharpMath**: правила раскладки TeX и настоящий математический шрифт (Latin Modern Math) в .NET. MathJax и
  KaTeX нужен движок JavaScript (Node или браузер); настоящий LaTeX (MiKTeX с dvipng) — отдельная установка TeX и процесс
  на каждую формулу (не пробовалось); WpfMath — это WPF, только Windows.
- **Охват** на 17 222 выносных формулах этих заметок: как есть CSharpMath читает 12 595 (73 %). Замены того, что
  пишут в заметках, а он не знает (обёртки `equation*` и `align*`, `gathered`, `\tag`, `\prime`, `\boldsymbol`,
  `\dfrac`, `\bigl`, `\theta=`, принятое за одну команду…; `Renderer.Normalize`), доводят до 17 119 (99,4 %), из них
  нарисованы 17 116. Остаются текстом: `\substack` 28, `aligned` больше чем с двумя колонками 13, `\overbrace` 8,
  `\rvert` 8, `\underset` 6, несколько более редких.
- **Скорость** на тех же формулах, в один поток: медиана 0,58 мс на формулу вместе с кодированием в Sixel, 90 % — не
  больше 1,75 мс, все — за 14,7 с; первая — около 0,2 с (читаются шрифты). Рисуются в своём потоке, сначала те, что на
  экране; пока картинка не готова, формула показывается текстом.
- **Раскладка видит новые картинки, только когда делается заново** (`FormulaImages.Taken`, затем
  `FormulaPicturesChanged`): картинка, пришедшая между раскладкой и отрисовкой одного кадра, давала строке другую высоту,
  чем у её рядов (поймал тест). При перекладке строка вверху окна остаётся на месте, так что картинки, пришедшие выше,
  страницу не сдвигают.
- **Размер**: шрифт — 0,75 высоты ячейки (15 точек при 20 у Windows Terminal), так что дробь занимает две-три строки,
  как в раскладке текстом. Медиана 22 колонки × 2 строки (текстом: 23 × 3), 90 % — не больше 43 × 4; вывод Sixel в
  медиане 3,7 КБ, 90 % — не больше 8,5 КБ, отправляется заново при каждом сдвиге картинки.
- **Чёткость**: Windows Terminal рисует Sixel по 10 × 20 точек на ячейку при любом шрифте и масштабирует под шрифт
  (14 × 28 в окне, где измерялось); тонкие штрихи выходили бледными рядом с текстом, поэтому покрытие возводится в
  степень 0,6, прежде чем стать одним из 16 оттенков между фоном и цветом формул темы.
- **Терминал**: атрибуты устройства и размер ячейки спрашиваются после старта ([tui.ru.md](tui.ru.md)), только когда
  настройка включена и модуль есть; терминал, не ответивший на оба вопроса, получает раскладку текстом. В UI-тестах
  модуль выключен (`BLUEEDIT_MATHIMAGES=off`): на компьютере, где идут тесты, он может быть установлен, а эмулятор
  экрана тестов (pyte) картинок не показывает.
- **Не сделано**: строчные формулы (`$…$`) картинками; картинки в режиме Source; терминалы кроме Windows Terminal не
  проверялись; протокол графики kitty (другой способ отправлять картинки) не используется.

### Картинки в Markdown (`MarkdownImages.cs`, `FormulaImages.GetImage`, `Sixel.Quantize`)

Пользователь спросил 26 октября 2026: «а можно ли в таком редакторе показывать и изображения?» — в конспектах
графики и схемы рядом с текстом. Всё, что нужно картинке формулы, уже было (размер ячейки, строки под картинку,
фоновая очередь, отправка при прокрутке), поэтому изображение идёт тем же путём, с двумя новыми частями.

- **Чтение файла — дело модуля** (`Renderer.Decode`, `ImageApi = 1`): Skia, который там уже есть для формул, читает
  PNG, JPEG, BMP, GIF и WebP, поворачивает фото по EXIF и уменьшает с мип-картами (фото, уменьшенное в десять раз,
  остаётся гладким). Своего чтения картинок у редактора нет (в .NET его нет на Linux). Модуль без `Decode` (до 0.4.5)
  по-прежнему рисует формулы; меню говорит, что для картинок он стар.
- **Цветной Sixel** (`CellPicture` из пикселей, `Sixel.EncodeIndexed`): формула — маска покрытия, закрашенная цветом
  текста; картинке нужны свои цвета, не больше 255 (регистры Sixel; 256-й — фон, для прозрачных точек). Картинка с
  255 цветами или меньше сохраняет их точно. С большим числом получает палитру, подобранную под неё (median cut по
  каналам в 5 бит, цвет ячейки — среднее её точек), и рассеивание ошибки Флойда — Стейнберга. Сначала был фиксированный
  куб 6 × 7 × 6: сплошные столбики графика покрылись рябью (их синего в кубе не было), а Sixel вышел 78 КБ; с median
  cut столбики сплошные, Sixel 29 КБ, у фото 181 КБ вместо 227 КБ. Кодирование сначала раскладывает точки полосы по
  цветам, поэтому каждый использованный цвет стоит одного прохода по ширине.
- **Замеры** (график 900 × 520 и фото 1200 × 800, ячейки 10 × 20, не больше 95 столбцов на 20 строк): прочитаны,
  уменьшены и сведены к 255 цветам за 83 и 54 мс, закодированы за 16 и 15 мс, в фоновом потоке. Вывод раскодирован
  обратно (читатель Sixel на Python и ещё один в `ImageTests`) и просмотрен: цвета верные.
- **Где**: строка, где только картинка, `![подпись](путь)` или обсидиановское `![[имя|300]]`; не выше половины окна,
  чтобы текст вокруг оставался виден. Имена Obsidian ищутся там, куда его `.obsidian/app.json` кладёт вложения, рядом с
  заметкой и в корне хранилища, но хранилище не обыскивается: поиск идёт во время раскладки и не должен ждать большую
  папку. Найденный или не найденный файл проверяется снова через 2 с, поэтому сохранённая позже картинка появится, а
  изменённая прочитается заново (её время — часть ключа).
- **Не сделано**: картинки рядом с текстом, в списках и таблицах; картинки из интернета; анимация GIF; размер при
  прокрутке (Sixel фото отправляется заново, когда оно сдвигается; скорость Windows Terminal при 180 КБ на кадр ещё
  не измерена).

## Номера строк (`EditorView.Gutter.cs`)

- **Где.** Колонка слева от текста шириной в номер последней строки плюс пробел; строка с курсором — цветом текста,
  остальные — цветом комментариев. Всё, что ставит текст на экран — рисование, ширина мягкого переноса, курсор,
  попадание мышью, горизонтальная прокрутка, — работает в `TextArea`, области правее колонки, поэтому своего сдвига
  нигде не понадобилось. Щелчок по номеру ставит курсор в начало этой строки.
- **Перенесённые строки** нумеруются только на первом экранном ряду, как в VS Code; так же формула, разложенная на
  несколько рядов. Колонка расширяется, когда в файле становится больше 9, 99, … строк; раскладка переноса кэшируется
  по ширине ряда и тогда пересобирается сама.
- **По умолчанию выключены, одна настройка на все файлы** (`lineNumbers`). Alt+G (или View → Line numbers) включает
  и выключает их во всех открытых файлах и сохраняет настройку, так что при следующем запуске они такие, какими их
  оставили. В 0.2.4–0.2.5 они были включены в коде и выключены в прозе (`lineNumbersCode`, `lineNumbersProse`), а Alt+G
  действовала только на текущий файл и не сохранялась: переключение терялось с каждым открытым файлом, а номера мешали
  читать, и код тоже. Два старых ключа пропускаются без предупреждения.
- **Узкое окно**: если для текста остаётся меньше 20 колонок, номера не показываются.
- **Alt+G**: Alt+N (очевидная) уже делает нумерованный список; G — как в Ctrl+G, переход к строке.

## Состояние в меню (`MenuItem.On`, `Choice`, `Value`)

**Правило (пользователя, 26 октября 2026): если опция включена, это видно в меню, чтобы всегда было понятно, где мы
находимся.** У каждого пункта, который что-то переключает, есть отметка или значение; пункт без них — действие, и его
название говорит, над чем оно. Клавиша, переключающая настройку, сохраняет её, чтобы меню и Tools > Settings не
расходились. Новый переключатель сразу делается так.

Пользователь не мог понять, что включено сейчас: «Spell check on/off», «Line endings CRLF/LF» называли оба состояния,
а какое из них действует и что будет после нажатия, меню не говорило (26 октября 2026). Теперь, как в меню Far:

- `√` в пустой колонке перед подписью — то, что включено: перенос, номера строк, картинки формул,
  автоперенос, орфография, вертикальный блок. «Spell check on/off» стала «Spell check».
- `•` — выбранное из нескольких: режим Markdown (только в файле Markdown), тема.
- Значение справа, где стоит клавиша, у настройки с двумя значениями без клавиши: «Line endings … CRLF».

Состояние спрашивается при каждом рисовании меню (`Func<bool>`), поэтому никогда не устаревает и не хранится второй раз.

Ctrl+F12 (Format code) — действие, не переключатель, но и у него результат был не виден: отформатированный файл почти
такой же, а в строке состояния было «Formatted by ruff». Теперь там сказано, сколько строк изменилось («lines changed:
3»), или что программа ничего не изменила. Строки считаются без полного diff: строки нового текста, которых не было в
старом, или исчезнувшие, что больше (`App.ChangedLines`). Из названия пункта ушло «(language server)»: форматирует и
ruff или black.

Затем пользователь спросил, режимы ли Align left, right, centre и Justify и какой из них включён. Это действия, один
раз, над абзацем с курсором (или выделенными); теперь они называются «Paragraph: align left», «Paragraph: centre» и
так далее. И Tools > Settings показывало «Spell checking: on» после того, как F8 выключила орфографию: F8 и Alt+Z
меняли только редактор, а свою настройку сохраняла одна Alt+G. Теперь сохраняют все три (Alt+Z — для текста или для
кода, по файлу). У Formula pictures галочка стоит, пока настройка включена, даже если картинок нет, поэтому справа
сказано почему: «no module», «module failed», «not in this terminal».

Проверка 31 октября 2026 показала, что с переключателями всё в порядке, а дыра в пунктах с «...»: их окно хранило
состояние, которого меню не показывало, и чтобы узнать, чем проверяется текст, надо было открывать каждое. Теперь Tools
показывает его справа: Grammar checking (√ и названия проверок), Grammar model, Spelling languages, Spelling provider,
Style options («3/6»), Ignored rules (число, при нуле ничего), Command be in any console (√); File > Reopen with encoding
показывает кодировку. Значение запрашивается с каждым кадром, пока меню открыто, поэтому они читают то, что в памяти; имя
модели грамматики берётся из настройки, а не из списка папки моделей (Auto остаётся «авто», пока окно не открыто).
Исключение — одно чтение реестра для PATH, это микросекунды. Значение длиннее 24 символов обрезается с «…», иначе длинное
имя модели на сервере расширяло бы всё меню.

Меню Window перечисляет открытые файлы под Next и Previous, • у текущего, цифра как горячая клавиша (Alt+W, 2). Вкладки
показывают то же, но вкладке нужна мышь, и не все вкладки могут поместиться. В списке только первые девять: те, что
достаёт Alt+1..Alt+9, а прокрутки в меню нет; остальные — через F6 или вкладку. Такие пункты приходят из `Menu.More` и
запрашиваются при отрисовке. В имени файла может быть подчёркивание, поэтому горячую клавишу отмечает только первое
подчёркивание в названии.

## Назад и вперёд (`JumpHistory.cs`, `GoBack` в `App.Code.cs`)

Ctrl+G и оглавление ведут туда, куда знаешь, как попасть; «назад» возвращает туда, откуда ушёл, и номер строки помнить не
нужно. Раньше это делала Shift+F12 и только после F12. Search > Go back и Go forward, Alt+Left и Alt+Right, как в браузерах
и IDE (и во Fresh, на который посмотрели 29 октября 2026); Shift+F12 остаётся второй клавишей для «назад».

- **Записываются только переходы**: Ctrl+G, поиск и F5, оглавление, следующая ошибка, F12, выбор из результатов по папке
  или ссылок. Стрелки, мышь и набор — нет: иначе возвращаться пришлось бы по букве. Смена файла (F6, вкладка) и открытие
  тоже не переходы, у них свои пути назад; место в другом файле всё равно находится.
- **Серия считается за один переход.** Пять нажатий F5 — один переход: «назад» возвращает туда, где поиск начался, как и
  нужно после просмотра совпадений. Серия заканчивается, если курсор сдвинулся с места последнего перехода или переход
  другого рода: нашли совпадение, поправили там, F5 дальше — и «назад» вернёт к правке. То же для Shift+F7. Отвергнуто:
  записывать каждое совпадение, ведь «назад» снова прошёл бы по всем.
- Новый переход сбрасывает места «вперёд», как в браузере. Хранится сто мест.
- **Правка не сдвигает места**: текст, вставленный выше, смещает место на несколько строк, а за концом укороченного файла
  оно ограничивается концом. Следить за правками значило бы менять все места при каждом нажатии клавиши ради разницы в
  пару строк при возврате. Не стали.
- У несохранённого файла нет имени, поэтому место говорит только об этом; из нескольких таких берётся первый. Место в
  закрытом файле открывает его снова, место в исчезнувшем файле пропускается.
- **Alt+стрелки и панели.** Windows Terminal по умолчанию отдаёт Alt+стрелки переходу между панелями (`Terminal.MoveFocus*`).
  Замерено в Windows Terminal 1.25 в Sandbox 31 октября 2026: без панелей обе клавиши доходят до редактора. С двумя панелями
  рядом терминал забирает ту клавишу, в направлении которой есть панель, и фокус уходит туда, а другую пропускает: в левой
  панели Alt+Left идёт назад, а Alt+Right меняет панель; в правой Alt+Left меняет панель. Поэтому то же делают Shift+F12 и
  Ctrl+Shift+F12. В меню названы Alt+Left и Alt+Right, как более привычные, а F1 даёт обе пары: чем пользуются люди, узнаем от
  них. Alt+Up и Alt+Down, двигающие строки, встречают то же при панелях друг над другом.

## Парная скобка (`GoToMatchingBracket` в `EditorView.Code.cs`)

Ctrl+] переходит к паре скобки у курсора или сразу перед ним и оттуда обратно. Использует тот же поиск, что подчёркивает
пару в коде (до 1000 строк, строки и комментарии пропускаются), но в отличие от подчёркивания работает и в Markdown и обычном
тексте, для длинного `\frac{...}{...}`. Только `( [ {`: у `$` и блоков кода не отличить открывающий от закрывающего без
разбора блока, поэтому их нет. Туда и обратно считается за один переход для Alt+Left. Ctrl+] свободна в настройках
Windows Terminal 1.25 по умолчанию; на Windows она приходит как клавиша, в других системах как 0x1D.

## Выделение по смыслу (`SelectionSteps.cs`, `EditorView.SelectByMeaning.cs`)

Alt+= выделяет следующий по размеру кусок вокруг выделения; Alt+- возвращает на шаг. Выделяя вручную, приходится следить,
где кусок начинается и кончается; здесь границы находятся сами. Дальше как обычно: набор заменяет, Del удаляет, Ctrl+X
вырезает. То, что vi делает через `ci"`, только без режима.

- **Нет жёсткого порядка шагов.** Каждый вид куска предлагает кандидатов (слово; между кавычками, `$` или скобками, затем
  вместе с ними; предложение; строка; блок по отступу в коде; абзац; раздел; файл), и побеждает наименьший, содержащий
  выделение и что-то ещё, так что отдельные лестницы для текста и кода не нужны.
- **Кусок, пересекающий скобки или блок, не предлагается.** Первая версия предлагала строку: от `d` в `[c,⏎  d])` брала
  `d])`, вокруг которой скобок уже нет, и до скобок было не дойти. Это нашёл модульный тест.
- **Предложения определяются приблизительно**: точка, `!` или `?`, за которыми пробел или конец строки, не внутри `$...$`.
  Точка после сокращения («т. е. ») здесь заканчивает предложение; словарь на каждый язык того не стоил. Апостроф в тексте
  не кавычка («don't»), в коде кавычка.
- В коде скобки в строках и комментариях не считаются (`IsCode`, как для подчёркивания пары); до 1000 строк в каждую сторону.
- Alt+- помнит состояния, из которых шёл Alt+=, только пока выделение то самое, что оставил Alt+=: любое движение или набор
  их забывает.
- **Клавиши.** Expand Selection во Fresh (посмотрели 29 октября 2026) без клавиши и в Markdown лишь добавляет следующее
  слово. Alt+Shift+стрелки из VS Code по умолчанию заняты Windows Terminal, как и Ctrl+Shift+Up и Down, а Ctrl+Shift+Space
  открывает его меню новых вкладок (`defaults.json` версии 1.25). Alt+= и Alt+- там свободны.

## Прокрутка в режиме чтения (`EditorView.ScrollReading`)

- Курсор в режиме чтения не рисуется, но стрелки двигали его, как при правке: страница стояла, пока невидимый курсор не
  доходил до края, а первая стрелка после колеса мыши отбрасывала экран назад к курсору (замечено в работе,
  10 октября 2026).
- Теперь клавиши двигают страницу, как в просмотрщике: ↑/↓ — на строку, PgUp/PgDn и Пробел/Shift+Пробел — на страницу,
  Home/End — в начало и в конец (последняя страница полная); колесо — на 3 строки, как везде. Невидимый курсор
  держится на первой показанной строке, так что Ln в строке состояния, поиск и выход из режима чтения продолжаются от
  того, что на экране.

## Число строк в строке состояния

`Ln 12/340`: строка курсора и число строк. Число — редактора, то же, которым кончаются номера строк и до которого
доходит Ctrl+G: у файла, который кончается переводом строки, есть пустая последняя строка, на которую можно встать,
поэтому оно на единицу больше, чем у `wc -l`.

## Окно настроек (`ShowSettings`, `OptionsDialog`)

Настройки хранятся в `settings.json` с комментариями, как у Windows Terminal и VS Code: всё в одном месте, с пояснениями,
легко перенести на другой компьютер. Tools > Settings открывал этот файл, и только. Пользователь попросил и форму, или
то и другое (11 октября 2026); из файла он к тому же не нашёл, как вернуться к тексту (теперь это делает Esc,
`EditorView.EscapeCloses`).

Значит, то и другое: окно показывает основные настройки списком, у каждой свои значения (Пробел или ← → меняют, под
списком — пояснение к выбранной), как в окнах настройки Far; последний пункт открывает файл, в котором есть всё. Enter
записывает в тот же файл только изменённое — через `Settings.SetValue`, который сохраняет комментарии и вид файла, — и
сразу применяет, как всегда делал View > Theme. Хранилище одно, а всё, чего окно не показывает (проверка грамматики,
серверы языков, модели, цвета), остаётся в файле. В окне нет списков и путей, а также настроек, у которых уже есть своё
меню (Grammar checking, Spelling languages, шрифт терминала).

## Вид окон и окно F7 (`Draw.Box`, `FixDialog`)

Окна сохраняют вид DOS: светлое окно в жирной рамке, заголовок врезан в неё, справа и снизу тёмная тень, падающая на
текст. 24 октября 2026 рядом попробовали вид как в Far (поле в 2 колонки и 1 строку вокруг тонкой двойной рамки,
заголовок по центру) и сняли оба в настоящей консоли в Windows Sandbox: пользователь почти не увидел разницы, а поле
отнимало место (высокие окна, настройки и справка, закрывали строку меню и строку клавиш). Поэтому оставили как было.

Плохо было окно F7. Оно было списком: варианты, потом строки `[ Ignore ]` и `[ Never show this ]`, а объяснение
проверки стояло в заголовке, обрезанное по ширине рамки («The plural subject "examples" takes the plural verb…»).
Пользователю были непонятны три вещи: выделенная строка — синяя полоса во всю ширину — читалась как поле для ввода;
вариант `check` — как команда или как проверяемое слово; имя модели рядом (`check — claude-haiku-5-5: …`) — как ещё
один выбор, хотя модель задаётся в настройках и здесь не меняется. Стрелка `►` у выбранной строки и строка клавиш под
списком не помогли: это всё равно был не список однородных вещей.

Теперь окно устроено как всплывающее окно плагина для Obsidian (`obsidian-blueproof`, `src/editor/popup.ts`): что
сделать, потом почему, потом мелко — кто так считает и как скрыть. `FixDialog`:

```
┏┥Грамматика: «checks»┝━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓

┃ [► check ◄]                                                    ┃   исправления — кнопки
┃                                                                ┃

┃ [  Пропустить  ] [  Больше не показывать  ]   claude-haiku-5-5 ┃   действия; справа серым — кто нашёл

```

- Кнопки выглядят и ведут себя как в других вопросах (`ButtonDialog`): `► ◄` на той, что нажмёт Enter; Tab и ← →
  идут по всем, ↑ ↓ — к первой кнопке строки выше или ниже, Esc закрывает. Клавиш-букв нет: исправления — слова, их
  первые буквы совпадали бы.
- В заголовке — слова, о которых речь. Исправление другого отрезка текста (находка другой проверки рядом) говорит, что
  меняет: `examples checks → examples check`. Объяснение каждой проверки показано один раз, чужое — с её именем.
  Справа в нижней строке — проверки, у LanguageTool с правилом (`LanguageTool · AGREEMENT_SENT_START`): то, что
  выключит «Больше не показывать».
- Если исправления нет (LanguageTool часто только называет ошибку), это сказано на месте кнопок.
- Окно орфографии (`Орфография: «recieve»`: варианты, «Добавить в словарь», «Пропустить», справа `орфография: Windows`),
  слово вперемешку латиницей и кириллицей и правило записи формулы (`LaTeX`) — то же окно.

Остальные списки (оглавление, выбор файла, кодировки, модели) остаются списками, без стрелки: там строки однородны,
выбирается одна из многих, ↑ ↓ ходят по ним.

Остальные окна 24 октября 2026 разобрали так же: каждое открыли и сняли (скрипт гонял редактор в псевдоконсоли). У

- **Tools > Set up grammar checking**: *Remove...* стоял строкой среди способов проверять грамматику; теперь это

- **Tools > Grammar checking**: квадратики говорят, что отметить можно несколько, а отметка одной снимала остальные,

## Отступ после начала блока (`EditorView.BlockOpens`)

Enter сохранял отступ строки выше, и только: после `def func():` курсор вставал в начало строки (пользователь,
11 октября 2026: «не умеет элементарных вещей»). Теперь при `autoIndent` строка, которая кончается (не считая пробелов)
началом блока, даёт новой строке шаг отступа больше (`tabSize`): `:` в Python и YAML; `{`, `[`, `(` в C#, C/C++, Java,
JavaScript, Go, Rust, PowerShell, JSON и shell. Если курсор между открывающей и закрывающей (`{|}`, как делает
`autoClose`), закрывающая уходит на свою строку с отступом открывающей, как в VS Code. Простой текст, Markdown и другие
языки только сохраняют отступ. Не сделано: комментарий после `:` (`if x:  # note`) не учитывается, и ничего не
уменьшает отступ само после `return` или при наборе `}`.

## Основы правки кода (`EditorView.Code.cs`)

Попросили 11 октября 2026 («чего ещё не хватает редактору кода»), сделано как в VS Code:

- **Ctrl+/** закомментирует строку или выделенные строки комментарием языка (`#`, `//`, `--`, `::` в Batch) на их
  наименьшем отступе или раскомментирует, если все они уже комментарии. Терминалы присылают Ctrl+/ как 0x1F (Ctrl+_),
  поэтому работают обе клавиши; проверено вручную в Windows Terminal. **Только в латинской раскладке**: измерено
  отправкой в консоль тех событий клавиш, что шлёт Windows Terminal, и чтением того, что получает программа. Ctrl+S в
  русской раскладке (символ события 0 или «ы») всё равно приходит как 0x13 — Ctrl+буквы консоль переводит по
  клавише, — а Ctrl+/ там (та же клавиша печатает «.») не приходит вовсе или приходит обычной «.». В терминальном
  протоколе нет кода для Ctrl со знаком препинания; саму клавишу даёт только win32-input-mode Windows Terminal,
  которого нет в других терминалах, поэтому оставлено как есть (так договорились 11 октября 2026); если
  понадобится — вторая клавиша на букве.
- **Alt+↑ / Alt+↓** переносят строку или выделенные строки за соседнюю, курсор и выделение — вместе с ними. Не
  проверено: оставляет ли Windows Terminal Alt+стрелки себе для перехода между панелями, когда их в вкладке несколько.
- **Закрывающая скобка, набранная на пустой строке** (до курсора одни пробелы), в языках со скобками встаёт на отступ
  строки с её открывающей, найденной подсчётом скобок вне строк и комментариев.
- **Скобка у курсора** (на нём или прямо перед ним) **и её пара** рисуются жирными и подчёркнутыми. Пара ищется
  не дальше 1000 строк в каждую сторону, в каждом кадре, вне строк и комментариев; токены строк кэшируются, так что
  поиск — это просмотр символов.

## Форматирование языковым сервером (`FormatCode` в `App.Code.cs`, `EditorView.ApplyEdits`)

Ctrl+F12 просит у сервера файла `textDocument/formatting`, а для выделенных строк — `textDocument/rangeFormatting`, если
сервер это умеет. Умеет ли, видно из возможностей в его ответе на `initialize` (`documentFormattingProvider`,
`documentRangeFormattingProvider`), они хранятся у каждого сервера; pyright не предлагает ни того, ни другого
(проверено на pyright 1.1.414), csharp-ls — оба (0.28.0).

- **Набор не ждёт.** Ответ приходит в фоне (не дольше 30 с) и применяется через `TuiApp.Post`, только если версия
  правок файла та же, о которой спрашивали; иначе он отбрасывается с сообщением.
- **Правки — один шаг отмены.** Все TextEdit сервера относятся к тексту, который ему дали, поэтому они применяются от
  последней к первой в одной строке; пересекающиеся или выходящие за текст правки отбрасывают весь ответ. Курсор
  сдвигается на то, что изменилось до него, и остаётся на своём тексте.
- **Клавиша.** Сначала пробовали Ctrl+Alt+L (JetBrains): измерено отправкой в консоль тех событий клавиш, что шлёт
  Windows Terminal, — Ctrl+Alt+L приходит как обычный Ctrl+L (0x0C, без ESC): консоль Windows принимает Ctrl+Alt за
  AltGr, — а Ctrl+L удаляет строку. Shift+Alt+F (VS Code) приходит как ESC F и отличается от Alt+F меню File (ESC f)
  только регистром буквы, который переворачивает Caps Lock. Ctrl+F12 доходит целым (`ESC [24;5~`) и стоит рядом с F12
  (определение) и Shift+F12 (назад).

### Программы-форматировщики (`Formatters.cs`)

У pyright нет форматировщика, а чаще всего редактором пользовались для Python, поэтому Ctrl+F12 умеет запускать и
отдельную программу (попросили 11 октября 2026: «вызов внешних программ не проблема, главное чтобы это было изящно
продумано и не составляло проблем для пользователя»).

- **Какая.** Первым идёт форматировщик из настройки `formatters` (его выбрал пользователь); затем форматировщик
  языкового сервера, если он есть; затем первый установленный по умолчанию — для Python ruff, затем black. ruff
  первым: одна программа без Python, а на обычном коде его результат совпадает с black (он так задуман).
- **Как.** Текст идёт программе на стандартный ввод, `--stdin-filename` сообщает путь файла, запускается она в папке
  файла: поэтому находит `pyproject.toml` / `ruff.toml` проекта (проверено: `quote-style` у ruff,
  `skip-string-normalization` у black), и сохранять текст не нужно. UTF-8 в обе стороны (`PYTHONIOENCODING` для black
  на Windows). Ненулевой код выхода оставляет текст как есть; первая строка ошибок — в строку состояния. Не дольше
  30 с, потом программа завершается принудительно.
- **Одна правка.** Вывод заменяет только часть между общим началом и общим концом старого и нового текста
  (`Formatters.Diff`) и применяется тем же `ApplyEdits`, что и правки сервера: один шаг отмены, курсор вне изменённой
  части остаётся на своём тексте. Настоящий построчный diff для этого не понадобился.
- **Весь файл.** ruff (`--range`) и black (`--line-ranges`) умеют форматировать строки, но с разными аргументами и
  минимальными версиями; пока не сделано: с выделением форматируется весь файл, и сообщение об этом говорит.
- **Где искать black.** `pip install --user black` кладёт `black.exe` в `%APPDATA%\Python\Python3xx\Scripts`, а pip
  только предупреждает, что этой папки нет в `PATH`; `LspClient.Resolve` ищет и там. На Linux `~/.local/bin` pip уже
  просматривалась.
- **Установка.** `install.ps1 -Python` ставит ruff через winget (`astral-sh.ruff`, для пользователя, без прав
  администратора); `install.sh --python` берёт архив релиза ruff с GitHub в `~/.local/bin`, потому что pip в Ubuntu
  24.04 отказывается ставить с `--user` (PEP 668). Проверено в WSL: ruff 0.17.0 скачался и форматирует.

## Переименование (`RenameSymbol` в `App.Code.cs`)

Ctrl+F2 просит у сервера `textDocument/rename` и применяет WorkspaceEdit из ответа.

- **Клавиша.** В VS Code переименовывает F2, но здесь F2 сохраняет (как в Far и DOS-редакторах); Shift+F6
  (JetBrains) переходит к предыдущему документу. Ctrl+F2 сохраняет F2 в названии и доходит целым (`ESC [1;5Q`).
- **Сначала — можно ли.** Если сервер умеет `prepareRename` (pyright и csharp-ls умеют), его спрашивают до окна с
  именем: в строке или на ключевом слове он отвечает null, и сообщение говорит об этом вместо окна, которое никуда не
  ведёт. Но null на имени в коде не принимается на веру: на одной из машин CI pyright сразу после запуска ответил null на
  `greet` (почему — не выяснено; локально отвечает), поэтому там окно всё равно открывается и решает ответ самого
  переименования; в строке или комментарии (по токенам самого редактора) сообщение — сразу. Его диапазон или
  подсказка дают старое имя; иначе — слово под курсором. Окно показывает старое имя, набор
  заменяет его (замена при наборе в `TextInput`, как последний запрос в окне поиска).
- **Неоткрытые файлы.** Правки применяются через редактор ко всем файлам — открытым на месте, остальным с открытием
  во вкладке — и на диск ничего не пишется. VS Code делает так же; причина здесь: переименование по нескольким файлам
  хочется посмотреть, у каждого файла свой шаг отмены, а **File → Save all** (добавлено вместе с ним) записывает их.
  Сообщение считает изменения, файлы и открытые.
- **Что отвергается.** WorkspaceEdit, который ещё и создаёт, переименовывает или удаляет файлы (`documentChanges` с
  `kind`): ничего не применяется, сообщение говорит почему. Правки, не подходящие к тексту файла (он изменился с тех
  пор, как сервер его прочёл), оставляют этот файл как есть, и он называется в сообщении.
- **Не сделано:** о новом тексте других файлов сервер узнаёт, только когда каждый из них показан (текст показанного
  файла уходит серверу каждый такт), поэтому подчёркивания в них до тех пор могут отставать.

## Использования (`FindReferences` в `App.Code.cs`)

Alt+F12 просит у сервера `textDocument/references` (вместе с объявлением) и показывает места в том же списке, что уже
был у поиска в папке (Alt+F7): по строке на место с файлом, номером строки и её текстом; Enter открывает файл с
выделенным именем, а Search → Folder results возвращает последний список, чем бы он ни был заполнен.

- **Клавиша.** Shift+F12 из VS Code здесь — возврат после F12; его Shift+Alt+F12 — три клавиши. Alt+F12 стоит рядом с
  F12 (определение), Shift+F12 (назад) и Ctrl+F12 (форматирование) и доходит целым (`ESC [24;3~`).
- **Строки** берутся из открытого документа, если файл открыт (его несохранённый текст, который есть и у сервера), а
  иначе с диска. Пути показываются относительно корня проекта, в котором работает сервер.
- **Порядок** — по файлу и строке, а не как прислал сервер (у pyright без сортировки); список начинается с места под
  курсором, так что стрелки ведут к соседним.

## Структура кода (`ShowOutline` в `App.Search.cs`, `LanguageServers.OutlineFrom`)

Ctrl+O, заголовки файла Markdown или LaTeX, для файла с кодом показывает его символы из `textDocument/documentSymbol`.

- **Деревья — по запросу.** Без `hierarchicalDocumentSymbolSupport` в возможностях клиента pyright отвечал плоским
  списком SymbolInformation (измерено: его локальные `name`, `word` пришли как переменные `greet`) и диапазоном всего
  определения (столбец 0, а не имя); с ним — деревом DocumentSymbol с диапазоном самого имени. Читаются обе формы: в
  плоском списке уровень берётся из `containerName`.
- **Локальные — не показываются.** Дети функции, метода или конструктора — это её параметры и локальные переменные, а
  не структура. Они отбрасываются в обеих формах (в плоском списке — по виду контейнера).
- **Список** показывает каждый символ с отступом по уровню и видом справа, начинается с последнего символа на строке
  курсора или выше, Enter переходит к имени.

## Быстрые исправления (`QuickFix` в `App.Code.cs`)

F7 на ошибке или предупреждении в коде, который показывал сообщение, сначала просит у сервера `textDocument/codeAction`
для диапазона находки и передаёт саму находку так, как её прислал сервер (`LspDiagnostic.Raw`: Roslyn подбирает
исправления по коду и данным диагностики, которых в разобранной записи не было).

- **Клавиша.** Ctrl+. из VS Code терминал передать не может (измерено: `docs/tech/editing.md`, «Основы правки кода»);
  Alt+Enter из JetBrains — полноэкранный режим Windows Terminal. F7 уже значил «что здесь не так и что делать» для
  орфографии и грамматики, а Shift+F7 уже переходит к следующей находке в коде.
- **Что объявляет клиент.** `codeActionLiteralSupport` (иначе серверы могут отвечать одними Command), `isPreferredSupport`,
  `disabledSupport`, `dataSupport`, `resolveSupport` для `edit` и `workspace.applyEdit`.
- **csharp-ls не кладёт правку** (измерено, 0.28.0): в его действиях только заголовок и `data`; правка приходит из
  `codeAction/resolve`, когда действие выбрано. Его предпочтительное `using System.Text;` — первым в списке; остальные
  (создать тип в этом или новом файле…) — в его порядке. Отключённые действия не показываются.
- **Команды.** Действие, которое является командой (или содержит её), отправляется обратно через
  `workspace/executeCommand`; сервер может прислать `workspace/applyEdit`, клиент сразу отвечает, а редактор
  применяет правку в своём потоке.
- **Применение** — как у переименования: каждый файл — один шаг отмены, неоткрытые файлы открываются несохранёнными.
- **pyright не предлагает ничего** для неопределённого имени (измерено на 1.1.414): там F7 показывает сообщение, как
  раньше.

## Инструменты для кода, которые ставит редактор (`CodeTools.cs`)

Как поставить языковые серверы на компьютер, было самым трудным (как сказал один пользователь, «вопрос на миллион —
как сделать это изящно»). Отрабатывалось это на двух Linux-машинах: на NAS, где нет ни apt, ни opkg, нет Node.js и
.NET, и на сервере с Ubuntu 24.04, где есть node без npm, а apt требует sudo. Обе — x86_64 с glibc 2.39, на которой
работают собственные сборки проектов, поэтому редактор ставит их сам, в одну свою папку, без root:

- **Node.js**: новейшая LTS из `nodejs.org/dist/index.json`, её `.tar.gz` (xz не нужен: .NET читает tar и gzip, но не
  xz) или `.zip`, сверка с `SHASUMS256.txt`. Затем pyright этим npm в `tools/npm` (`npm install --prefix`, без
  глобальной папки). Если Node.js с npm уже есть в `PATH`, берётся он.
- **ruff**: `github.com/astral-sh/ruff/releases/latest/download/<архив>`, сверка с `.sha256`, лежащим рядом; без API
  GitHub (без ограничения на число запросов).
- **.NET SDK 10**: новейший SDK из метаданных выпусков Microsoft
  (`builds.dotnet.microsoft.com/dotnet/release-metadata/10.0/releases.json`), где у каждого архива есть адрес и SHA-512.
  Сначала был скрипт Microsoft `dotnet-install.sh`, но ему нужен bash, а на NAS только busybox `sh` (измерено: «bash:
  not found»); через метаданные не нужна оболочка, и архив проверяется. Затем csharp-ls через
  `dotnet tool install --tool-path`. Если SDK уже есть в `PATH`, берётся он.
- **Поиск и запуск**: `LspClient.Resolve` ищет в папке после `PATH`; `LspClient.StartInfo` ставит наши Node.js и .NET
  первыми в `PATH` запускаемой программы (загрузчик pyright запускает `node`) и задаёт `DOTNET_ROOT` (загрузчик
  csharp-ls ищет .NET там, если он не в системном месте).
- **Измерено**: на Windows (PATH урезан до System32) pyright и ruff поставились из меню и из командной строки: Node.js
  24.21.0, pyright 1.1.414, ruff 0.17.0 (Node.js 102 МБ, pyright 19 МБ, ruff 25 МБ), потом Ctrl+F12 отформатировал
  этим ruff. На сервере с Ubuntu 24.04 `be --install-tools` поставил все три; запуск только с ними в `PATH`:
  csharp-ls 0.28.0, pyright 1.1.414, ruff 0.17.0. Размеры там: Node.js 208 МБ, pyright 38 МБ, .NET 624 МБ, csharp-ls 99 МБ, ruff 23 МБ.
- **На NAS** (busybox, без менеджера пакетов): все три поставились через `--install-tools`; pyright 1.1.414, ruff 0.17.0
  и csharp-ls 0.28.0 (.NET SDK 10.0.401) работают только с ними.
- **TypeScript и JavaScript: собственный сервер TypeScript 7.** Сначала пробовался typescript-language-server (обычный
  выбор, обёртка над `tsserver.js` из пакета typescript) через npm рядом с pyright: с `typescript@latest`, теперь это
  7.0.2, он останавливался с «Could not find a valid TypeScript installation» (измерено): TypeScript 7 — родная
  программа, `tsserver.js` в нём нет. Зато у его `tsc` есть свой сервер, `tsc --lsp --stdio`. Он выходит отдельным
  пакетом npm на каждую систему, `@typescript/typescript-<ос>-<архитектура>`, с программой и её `lib.*.d.ts`; редактор
  берёт архив, который реестр называет для `latest`, и сверяет SHA-512 из его `integrity`, так что не нужны ни Node.js,
  ни npm: 9 МБ скачать, 27 МБ на диске против примерно 240 МБ с Node.js для обёртки. Программа для Linux собрана статически и
  работает на NAS. Запускается по полному пути: `tsc` в `PATH` — обычно TypeScript 5 из npm, где `--lsp` нет.
- **Находки по запросу.** TypeScript 7 сам находки не присылает (измерено: ничего за 4 с после `didOpen`); он объявляет
  `diagnosticProvider` и отвечает на `textDocument/diagnostic`. Поэтому клиент после каждой правки спрашивает каждый
  сервер, который это объявил, а при `interFileDependencies` — про все его открытые файлы; ответы идут туда же, куда
  присланные.
- **Программы `.cmd` в папке с пробелом**: npm из `C:\Program Files\nodejs` не запускался («'C:\Program' is not
  recognized»), потому что `cmd /s /c` снимает первую и последнюю кавычку строки; теперь строка берётся в кавычки ещё
  раз. Встретилось при установке через системный npm, на этом же споткнулась бы и установка pyright.
- **Не сделано**: обновление по расписанию (повторная установка обновляет); архивы для macOS; .NET SDK из метаданных на
  Windows не пробовался (там нашёлся и использовался SDK из `PATH`).
- Окно со списком теперь расширяется до самой длинной строки (не шире экрана), а не обрезает строки на 60%.
