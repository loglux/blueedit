# Терминальный слой (`src/Tui`)

English: [tui.md](tui.md).

BlueEdit не использует библиотеку для текстового интерфейса. `src/Tui` (около 1800 строк, свой проект `Tui.csproj`,
без зависимостей) читает ввод терминала, хранит сетку ячеек и отправляет терминалу только то, что изменилось.
Редактор (`EditorView`, `MainView`, `App`) рисует в эту сетку и получает от слоя события.

## Зачем свой

Сначала редактор работал на [Terminal.Gui](https://github.com/gui-cs/Terminal.Gui). Его заменили 2 октября 2026 года
(коммиты `31925c6`, `fc31e26`, слияние `8016836`) по таким причинам:

- **Задержка при наборе.** Terminal.Gui опрашивал консоль раз в 20 мс. От нажатия клавиши до символа на экране
  проходило **43–55 мс** (замер на Markdown-файле в 2000 строк). На своём слое — **4,8 мс медиана, p95 9 мс** (окно
  120×30), 9 мс на 220×50. Поток ввода теперь ждёт консоль и просыпается в момент прихода байта. «Набор никогда не
  ждёт» — первое правило проекта, и это была самая большая отдельная потеря.
- **Ctrl+Z.** Поток консоли .NET (и `ReadFile`) в Windows считает Ctrl+Z концом ввода: после первого Ctrl+Z ввод
  прекращался. Windows-часть читает через `ReadConsoleW`, у которого этой беды нет.
- **Контроль над выводом.** Отправляются только изменившиеся ячейки, одной записью на кадр; 24-битный цвет; мышь SGR;
  bracketed paste (вставленный текст приходит одним событием, поэтому это один шаг отмены и без автоотступа).
- **Перенос на другие системы.** Всё, кроме чтения байтов, сырого режима и размера окна, одинаково на всех системах.
  Linux-часть (`UnixPlatform`, октябрь 2026) — около 100 строк, и после неё весь редактор заработал на Linux.

Цена: диалоги, меню и виджеты пишем и поддерживаем сами (`Dialogs.cs`, `MenuBar.cs`, `Widgets.cs`), и то, что
библиотека дала бы даром (например, широкие символы), приходится добавлять руками.

## Как это устроено

```
 терминал ──байты──► ITerminalPlatform ──символы──► InputParser ──события──► очередь ──► цикл TuiApp ──► Root/Menu/Modal
 (Windows Terminal,   (WindowsPlatform,              (клавиши, мышь,          ▲                │
  xterm, ...)          UnixPlatform)                  вставка)                │ WakeInput       │ рисование
                                                                      TuiApp.Post(work)        ▼
 терминал ◄──одна запись на кадр── ConsoleHost.Present ◄── Screen.Flush (только изменения) ◄─ Screen
```

| Файл | Что делает |
|---|---|
| `Platform.cs` | `ITerminalPlatform`: чтение ввода, поток вывода, размер окна, включение и выключение сырого режима. `WindowsPlatform` (API консоли) и `UnixPlatform` (termios); `CreateForCurrentOs` выбирает нужный. |
| `ConsoleHost.cs` | Владеет терминалом, пока работает программа: сырой режим, альтернативный экран, отчёты мыши и вставки; поток ввода; поток размера; при выходе всё возвращает. |
| `InputParser.cs` | VT-ввод → `KeyInput`, `MouseInput`, `PasteInput`. Один разборщик на все системы. |
| `Events.cs` | Типы событий, `Key` и `Mods`. |
| `Screen.cs` | Сетка ячеек (двойной буфер) и `Flush`, который строит вывод, превращающий показанное терминалом в новый кадр. |
| `TuiApp.cs` | Главный цикл, `Post` / `Wake`, модальные диалоги, порядок рисования; `Theme`; рисование рамок. |
| `MenuBar.cs`, `Dialogs.cs`, `Widgets.cs` | Строка меню, диалоги (строка ввода, список с галочками, форма, кнопки, список, вопрос с ответом одной клавишей, окно файлов «Открыть» / «Сохранить как») и виджеты (однострочное поле, список). |
| `KeyboardLayout.cs` | Русская буква ЙЦУКЕН → латинская буква той же клавиши, чтобы Alt+F и ответы Y/N работали в любой раскладке. |

### Системы

- **Windows** (`WindowsPlatform`): режимы консоли — VT-ввод (`ENABLE_VIRTUAL_TERMINAL_INPUT`, без построчного ввода,
  без эха, без обработки Ctrl+C) и VT-вывод; кодовые страницы переключаются на UTF-8 (65001) и при выходе
  возвращаются. Ввод читается записями консоли через `ReadConsoleInputW`; в режиме VT-ввода каждая запись — один
  символ UTF-16, тот же текст, что давал `ReadConsoleW`. С `keyEvents` VT-ввод выключается, и записи несут клавиши
  (ниже).
- **Linux и macOS** (`UnixPlatform`): сырой режим termios через `cfmakeraw` из libc (без редактирования строки, без
  эха, Ctrl+C и Ctrl+Z приходят в редактор как клавиши). `struct termios` в Linux и macOS разная, поэтому она хранится
  как непрозрачные байты: читается `tcgetattr`, делается сырой средствами libc, записывается обратно. Ввод — байты UTF-8
  из `read(0)`, декодер помнит символ, разрезанный между двумя чтениями; чтение, прерванное сигналом (`EINTR`),
  повторяется. На Linux «libc» загружается как `libc.so.6`.

### Ввод

- `ConsoleHost` держит поток, который ждёт в `ReadInput`; прочитанное идёт через разборщик в очередь, которую ждёт
  главный цикл. Опроса нет, клавиша обрабатывается сразу, как пришла.
- **Одиночный ESC** — это либо клавиша Escape, либо начало последовательности. Разборщик его придерживает, и таймер
  хоста (`EscapeTimeoutMs`, 25 мс) выдаёт его как Escape, если следом ничего не пришло. `ESC x` — это Alt+x.
- Понимает: клавиши курсора и функциональные с модификаторами xterm (`ESC [ 1 ; 5 C` = Ctrl+→), мышь SGR
  (`ESC [ < b ; x ; y M/m`: нажатие, отпускание, перетаскивание, колесо), bracketed paste (`ESC [ 200 ~ … ESC [ 201 ~`),
  modifyOtherKeys (`ESC [ 27 ; mod ; code ~`) и CSI u (`ESC [ code ; mod u`, kitty). Управляющие символы становятся
  Ctrl+буква; BS — это Ctrl+Backspace (так его шлёт Windows Terminal). Символы за пределами базовой плоскости Unicode
  приходят как `?` (в ячейке один символ UTF-16).
- **Размер окна** опрашивается раз в 60 мс отдельным потоком. Консоль Windows в режиме VT-ввода событий об изменении
  размера не присылает, а на Unix опрос избавляет от обработчика SIGWINCH.

### События клавиш в Windows (`WindowsKeys`, #184)

Терминальная программа получает текст, а в тексте нет кода для Ctrl с пунктуацией: в русской раскладке клавиша «/»
печатает «.», и Ctrl+/ приходил как «.» или не приходил вовсе. Сочетания Far работают в любой раскладке, потому что
Far читает события клавиш. `"keyEvents": true` (по умолчанию; `BLUEEDIT_KEY_EVENTS=1` или `0` это перекрывает) делает то же. Один вечер это был
пробный режим, выключенный по умолчанию: пользователь проверил Ctrl+/ в русской раскладке в Windows Terminal 1.25.2733
(2026-10-18), он сработал, и пользователь попросил сделать режим основным.

**Замер** (2026-10-18) зондом в псевдоконсоли (pywinpty, как в UI-тестах): клавиши посылались так, как их шлёт
Windows Terminal (win32-input-mode), чтение через `ReadConsoleInputW`:

| послано | VT-ввод включён | VT-ввод выключен |
|---|---|---|
| F1, ↑, Ctrl+→ | VT-последовательность, по символу в записи, vk 0 | vk 0x70 / 0x26 / 0x27, Ctrl в состоянии |
| Ctrl+/ в русской раскладке | «.» | vk 0xBF, Ctrl |
| Ctrl+1 | «№» | vk 0x31, Ctrl |
| Alt+F в русской раскладке | ESC «а» | vk 0x46, «а», Alt |
| отчёт мыши SGR | его символы | запись события мыши |
| bracketed paste | символы вместе с маркерами | текст, vk 0, маркеры пропали |
| ответ на `ESC [ c` (device attributes) | его символы | **ничего** |
| ответы на `ESC [ 16 t` и OSC 4 | их символы | их символы, vk 0 |

Прежняя заметка в #184 говорила, что записи клавиш сохраняют vk и при включённом VT-вводе; этот зонд такого не увидел,
с одним исключением: при VT-вводе NUL (Ctrl+Space) приходит как собственный Ctrl+@ консоли (vk 0x40, без символа),
который `ReadConsoleW` читал как NUL. Первая версия его отбрасывала и сломала Ctrl+Space (CI, PR #214). Какая
клавиша печатает «@», зависит от раскладки (на раннере CI это был не vk 0x40), поэтому теперь любая запись с Ctrl без
символа считается NUL.

**Как устроено.** Записи превращаются обратно в VT-текст, который разборщик уже читает, так что после платформы ничего
не меняется: особые клавиши — в последовательности xterm; Ctrl или Alt с пунктуацией или цифрой — в CSI u с символом
клавиши в раскладке US (`ESC [ 47 ; 5 u`, Ctrl+/); Ctrl+буква — в управляющий символ, как раньше; Alt+буква — в ESC и
набранную букву (кириллицу переводит `KeyboardLayout`, как раньше); AltGr (правый Alt с левым Ctrl) печатает свой
символ. Enter, Tab и Escape остаются такими, какими их давал VT-ввод: с Ctrl на них ничего не назначено, а Ctrl+Enter
должен оставаться Enter. Записи мыши становятся отчётами SGR (нажатия и отпускания — по изменению зажатых кнопок,
движение с зажатой кнопкой — перетаскивание, колесо). Текст без кода клавиши, начинающийся с ESC, — ответ
терминала, он проходит как есть.

**Вставка** (замер в Windows Terminal 1.25.2733 зондом, который запустил пользователь, 2026-10-18): консоль
превращает её в записи клавиш — нажатие и отпускание на каждый символ, сотни за одно чтение (по 512 зонду, который
просил 512). Символы, для которых в текущей раскладке нет клавиши (латиница при русской раскладке), приходят с vk 0;
остальные (пробел, Enter, цифры, знаки) — с клавишей, которую для них нашла консоль. Набор даёт по одной записи за
чтение. Первая версия считала вставкой только символы с vk 0, поэтому каждый Enter вставки был набранным Enter с
автоотступом: лесенка (снимок пользователя). Теперь текст (обычные символы, Enter, Tab, символы без клавиши)
собирается за одно чтение. Вставке, введённой как набор, вредят её переводы строк, поэтому одной bracketed paste она
уходит, если в ней есть перевод строки или нажатий 16 и больше; короткая строка — набор (автодополнение открывается,
а закрывающая скобка текста перешагивает парную). Enter в конце остаётся набранным Enter: имя и Enter, набранные
пачкой (так делают UI-тесты; правило «три нажатия — вставка» сломало их диалоги), по-прежнему отвечают диалогу.
Отпускания не учитываются и вставку не режут. Чтение берёт до 4096 записей, так что вставка приходит немногими
кусками.

**Ответу на `ESC [ c` нужен VT-ввод** (по нему узнаётся Sixel): `QueryGraphics` включает VT-ввод, а события клавиш
возвращаются с ответом или через секунду. Клавиши, нажатые в эту секунду, приходят текстом, как раньше.

**Проверено**: unit-тесты (`WindowsKeysTests`); все 203 UI-теста с `BLUEEDIT_KEY_EVENTS=1` (harness шлёт клавиши как
Windows Terminal); UI-тест, набирающий Ctrl+/ в русской раскладке, который с VT-вводом падает. **Не проверено**:
настоящий Windows Terminal (как он шлёт вставку: если клавишами, а не текстом, вставленный текст придёт как набор, с
автоотступом), conhost без Windows Terminal, ConEmu и протокол kitty в Windows Terminal 1.25. По SSH на Linux помочь
может только протокол терминала: следующий раздел.

### Протокол клавиатуры kitty на Linux и macOS (#184)

По SSH редактор получает то, что терминал шлёт текстом, поэтому Ctrl+/ в русской раскладке приходит как «.». Протокол
клавиатуры kitty позволяет программе попросить клавиши в виде `ESC [ code : shifted : base ; mods u`, где *base* —
клавиша в стандартной латинской раскладке. При включённом `keyEvents` (по умолчанию) хост шлёт запрос `ESC [ ? u`;
только терминал, который на него ответил (`ESC [ ? flags u`), получает включение `ESC [ > 5 u` (флаги 1 — клавиши с
модификаторами escape-кодами, и 4 — альтернативные клавиши) и выключение `ESC [ < u`, когда настройку выключают, и при
выходе. Терминал без протокола получает только запрос, который такие терминалы пропускают (Neovim шлёт такой же). С
Ctrl или Alt разбор берёт клавишу base; обычный текст, Enter, Tab и Backspace приходят как раньше (флаг 8, все
клавиши кодами, не запрашивается).

Замерено 19 октября 2026 пробником на NAS, `ssh` из Windows Terminal 1.25 (вкладка PowerShell):

| клавиша | пришло |
|---|---|
| ответ на `ESC [ ? u` | `ESC [ ? 0 u` |
| Ctrl+/, русская раскладка | `ESC [ 1105 :: 47 ; 5 u` (47 — «/») |
| Ctrl+/, английская | `ESC [ 47 ; 5 u` |
| Ctrl+1, русская | `ESC [ 8470 :: 49 ; 5 u` («№», клавиша «1») |
| Alt+x | `ESC [ 120 ; 3 u` |
| Esc | `ESC [ 27 ; 129 u` (128 — включён Num Lock, не учитывается) |
| Enter, буква | `\r`, буква |
| Ctrl+S | `ESC [ 115 ; 5 u` |

Тот же `ssh` в псевдоконсоли системного conhost (так UI-тесты запускают программы), с клавишами, посланными как их
шлёт Windows Terminal, получил обычный текст: «.» на русский Ctrl+/, «№» на Ctrl+1, и ответа на запрос не было.
Windows Terminal запускает свою консоль (OpenConsole), которая протокол знает; системная на сборке 26300 — нет. На
Windows редактор пользуется своими событиями клавиш (выше), поэтому протокол запрашивается только там, где их нет.

**Проверено**: unit-тесты (`InputParserTests` с замеренными последовательностями, `KittyKeysTests` — запрос,
включение и выключение); пользователем 20 октября 2026 — сборка для Linux по SSH на NAS в Windows Terminal 1.25: Ctrl+/
в русской раскладке комментирует строку, остальные клавиши как раньше. **Не проверено**: kitty, WezTerm, foot, Ghostty.

### Главный цикл (`TuiApp`)

`Run` повторяет: выполнить отложенную работу, нарисовать, подождать событие (не больше 250 мс), обработать.
Правила, которые держат набор быстрым:

- **Ввод, который уже ждёт, обрабатывается до следующего кадра**: зажатая стрелка или быстрый набор не оставляют экран
  позади. Ограничено `CoalesceMs` (40 мс), чтобы при потоке ввода экран всё же обновлялся.
- **В этом потоке ничего медленного.** Орфография, грамматика, языковые серверы и модели работают в фоне. Когда
  приходит ответ, фоновый код вызывает `TuiApp.Post(action)`: действие встаёт в очередь, а `Wake()` кладёт
  `WakeInput` в очередь событий, ждущий цикл тут же возвращается и выполняет его. Там, где нужна только перерисовка,
  сравнивается счётчик `Version`.
- `Tick` (раз в `TickMs`, 500 мс) — для периодических проверок; в редакторе это проверка файлов, изменённых на диске,
  сообщения об упавших проверках грамматики и отправка правок языковому серверу. Пока открыто меню или диалог, он не
  вызывается.
- **Диалоги** (`RunModal`) крутят вложенный цикл и сразу возвращают результат, поэтому код выглядит как
  `if (Dialogs.Pick(...) is int i) ...`.
- Окно файлов (`FileDialog`, #92) устроено как в Far: Enter заходит в папку, `..` — вверх, а из корня диска — к
  списку дисков (туда же Alt+F1), F7 создаёт папку. С именем файла это «Сохранить как»: поле имени под списком
  принимает набираемый текст, Tab переключает между ними. Само окно ничего не спрашивает: заменить ли файл и создать
  ли отсутствующую папку набранного пути, спрашивает вызывающий код (`Dialogs.SaveFile`) окнами с кнопками, а «нет»
  открывает окно файлов снова там же. Длинный путь в заголовке сохраняет конец (текущую папку), а не начало.
- `Normalize` превращает Alt/Ctrl + кириллическая буква в Alt/Ctrl + латинскую букву той же клавиши.
- Порядок рисования: основной вид (редактор с его строками), строка меню, открытое меню, диалоги снизу вверх; курсор —
  у самого верхнего.

### Вывод (`Screen`)

- Два буфера: нарисованное сейчас и то, что показывает терминал. `Flush` сравнивает их и выдаёт только отличающиеся
  ячейки, цвет и атрибуты отправляет заново, только когда они меняются, плюс курсор. Один кадр — одна запись `Write`;
  если ничего не изменилось, вывода нет вовсе.
- Цвета 24-битные (`Style.Rgb`) или -1 — цвет самого терминала. Атрибуты: жирный, подчёркнутый, инверсия, курсив,
  тусклый.
- `Resize` и `Invalidate` заставляют перерисовать всё при следующем `Flush`.
- **Области прокрутки** (`UseScrollRegions`, настройка `fastScroll`): если строки только сдвинулись, попросить терминал
  сдвинуть их самому (область прокрутки + SU/SD), а не присылать заново. По умолчанию выключено: Windows Terminal
  показывал с этим строки не на своих местах, хотя тот же вывод через ConPTY в простом VT-эмуляторе верен.
- **Широкие символы** (`CharWidth`): восточноазиатские широкие и полноширинные символы и эмодзи из BMP, по умолчанию
  показываемые картинкой (`⚫`, `⭐`, `✅`), занимают две колонки терминала. Считаясь за одну, они сдвигали остаток
  строки на колонку, и сравнение буферов эту лишнюю колонку никогда не стирало: при прокрутке заметки с `### ⚫ Unknown
  — Not Yet Investigated` по экрану оставался столбик букв «d» (замечено в MobaXterm, воспроизведено под `script` на
  Ubuntu и проиграно через pyte; 0.2.4 и раньше). Теперь за широким символом идёт ячейка `Continuation`, в которую
  ничего не пишется; изменение любой половины перерисовывает символ целиком, а половина без второй половины (край
  всплывающего окна поверх) рисуется пробелом. Редактор так же строит показываемый текст (`Conceal.FitWidths`, шаг после
  скрытия разметки), поэтому курсор, мышь и мягкий перенос считают колонки как терминал; жёсткий разрыв не делит широкий
  символ или суррогатную пару. Эмодзи вне BMP (`🔴`) — суррогатные пары, и так две ячейки, и их ширина совпадала и раньше.
- **Символы нулевой ширины** (селекторы вариантов, соединители) не рисуются: `⚠️` рисуется как `⚠`, в одну колонку
  везде. С селектором терминалы расходятся в ширине (одна или две), так что никакой счёт не верен во всех.
- **Комбинируемые знаки** (Unicode Mn, Me: ударение, записанное отдельно от буквы, `e` + `◌́`, огласовки иврита и
  арабского) рисуются в ячейке предыдущего символа (`Screen.Set` со знаками, `Disp.Marks`), как их рисует любой
  терминал; знак в начале строки ставится на пунктирный кружок `◌`.
- **Эмодзи-последовательности** рисуются так, чтобы ни один терминал их не склеил, потому что терминалы склеивают по-разному
  (склеенная — одна картинка в две колонки, раздельно — каждая часть в своих): части, соединённые ZWJ (`👨‍👩‍👧`),
  показываются частями — соединитель не рисуется; оттенок кожи (`👍🏽`) не рисуется; два региональных индикатора флага
  (`🇬🇧`) рисуются своими буквами, `GB`. В тексте всё остаётся.
- **Курсор и Delete/Backspace** шагают по целым символам, как их видит читатель (графемные кластеры Unicode,
  `StringInfo.GetNextTextElementLength`): буква со знаками, суррогатная пара, эмодзи-последовательность, флаг. Раньше
  стрелка влево могла встать между половинками суррогатной пары, а Backspace — удалить одну половинку и сломать символ.
- **Картинки** (`Screen.Picture`, `CellPicture`, картинки формул редактора): картинка занимает целые ячейки и
  отправляется как Sixel. Что делает Windows Terminal 1.24 (10 октября 2026, пробная программа и снимки экрана): хранит
  картинку по ячейкам, и текст, записанный в ячейку, стирает картинку в ней; картинка высотой 20 или 40 точек (не целые
  полосы Sixel по шесть точек) строку под собой не трогает; после картинки курсор стоит на строке под ней, так что
  картинка на последней строке прокрутила бы экран. Отсюда: строки картинки помечаются в буфере ячеек; `Flush`
  отправляет каждую серию изменившихся строк одной картинки одним изображением Sixel на её место, до текста, а проход
  текста эти ячейки пропускает. Сдвинувшуюся или исчезнувшую картинку стирает текст, записанный в её старые ячейки;
  меню поверх картинки закрывает свои ячейки, а когда оно закрывается, эти строки отправляются заново. На последнюю
  строку ничего не ставится, а области прокрутки, пока на экране картинка, не используются. Картинка — маска покрытия,
  которая рисуется цветом текста ячейки поверх её фона (16 оттенков), каждая точка, так что всё под ней закрывается.
  Её ячейки сначала стираются (ECH, `CSI n X`): текст, поверх которого нарисована картинка, остаётся в терминале под
  ней, и знак, выходящий за свою ячейку (черта текстового интеграла `⎮`), после прокрутки оставлял точку-другую на
  строке под картинкой (видно в Windows Terminal 1.24, со стиранием пропало).
- **Вопрос терминалу** (`ConsoleHost.QueryGraphics`): атрибуты устройства (`CSI c`; 4 в ответе — Sixel) и размер
  ячейки в точках Sixel (`CSI 16 t`, ответ `CSI 6 ; h ; w t`) — после старта (в сыром режиме: до него ответ
  напечатался бы как текст), а размер ячейки ещё и после изменения размера окна. Ответы разбираются как
  `TerminalReply` и остаются в хосте (`Sixel`, `CellPixels`), во ввод не попадают. Windows Terminal отвечает
  `?61;4;6;7;14;21;22;23;24;28;32;42;52c` и `6;20;10t`: 10 × 20 точек на ячейку при любом шрифте.
- **Заголовок окна** (`Screen.Title`, `TuiApp.Title`): запрашивается каждый кадр и отправляется в нём (OSC 0), только
  когда изменился, без управляющих символов (они могут оказаться в имени файла). У редактора он такой:
  «notes.md * - BlueEdit». Раньше (0.3.0 и старше) его никто не задавал, и окно консоли показывало путь к `be.exe`
  (видно в прогоне новичка в Windows Sandbox). Прежний заголовок при выходе возвращается: на Windows `Console.Title`
  читается при запуске и отправляется обратно; в других системах он кладётся в стек заголовков xterm (`CSI 22;0 t`) и
  достаётся оттуда (`CSI 23;0 t`), а терминал без стека это пропускает. Через ConPTY заголовок доходит до терминала
  (UI-тест читает его в pyte); возврат прежнего заголовка тестом не проверен.

## Как это проверяется

- `tests/Tui.Tests`: разборщик (клавиши, модификаторы, мышь, вставка, последовательности, пришедшие по частям),
  сравнение кадров, виджеты и формы. Работают на Windows и Linux.
- `tools/TuiProbe`: маленькая программа на этом слое, показывает последнее полученное событие.
  `tests/ui/test_tui_layer.py` запускает её в настоящей консоли (winpty на Windows, ptyprocess на Linux) и проверяет, какими событиями
  приходят клавиши и вставка, и задержку: от записанной клавиши до символа на эмулированном экране — медиана меньше
  15 мс, p95 меньше 40 мс (сам стенд стоит около 6 мс).
- `tests/ui/test_performance.py`, весь редактор: клавиша → символ на большом Markdown-файле — медиана меньше 20 мс,
  p95 меньше 50 мс; обработка клавиши меньше 8 мс (медиана); стрелки в коде не перерисовывают экран (медиана кадра
  меньше 3000 байт; полная перерисовка — около 12 КБ).
- На Linux редактор проверен в псевдотерминале под WSL (ptyprocess + pyte): рисование, ввод кириллицы, стрелки,
  сохранение, выход, подчёркивание опечаток. Весь набор UI-тестов там тоже проходит: `tools/ci/check-linux.sh`.

## Грабли, на которые наступили

- C#: `"\x1b[2J"` работает, но `"\x1bD"` — не ESC + D: `\x` берёт до четырёх шестнадцатеричных цифр. Перед буквой,
  которая может быть шестнадцатеричной цифрой, писать `\u001b`.
- Windows: `ReadFile` и `Console.In` заканчивают ввод на Ctrl+Z — нужен `ReadConsoleW`.
- Консоль Windows в режиме VT-ввода не сообщает об изменении размера — размер нужно опрашивать.
- В шрифте старой консоли (Consolas в conhost — её открывает двойной щелчок по be.exe, когда Windows Terminal нет)
  нет `⟦ ⟧`: кнопки были квадратиками с вопросами (видно в Windows Sandbox, 21 октября 2026). Теперь они `[ ]`;
  `► ◄` в нём есть.
- WSL передаёт Linux-программам переменную `WT_SESSION` из Windows Terminal; это не значит, что запущена
  Windows-версия.
- UI-тест, который ждёт редактор доли секунды, падает, когда компьютер занят (docs/ci.md).
